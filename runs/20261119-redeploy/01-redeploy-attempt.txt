== findings (mechanics, new) ==
1. octl CreateVms BlockDeviceMappings WITHOUT DeviceName: the API
   rejects with 4019 "The provided value ('{name}') for the parameter
   'Device' is invalid" — a BSM override needs an explicit
   --BlockDeviceMappings.0.DeviceName (or no BSM at all). MS-5's
   DryRun-validated 50 GiB root payload must have carried one; DryRun
   does NOT surface this (the 4019 comes from the real call).
2. octl `--dry-run` (local) prints the exact request payload — use it
   to settle flag/encoding questions before real calls (userdata file
   is sent AS-IS: the --UserData file must already be base64).
3. QUOTA CHECKED (ReadQuotas, 12:5x UTC) — corrects the MS-5
   hypothesis. dedicated_server_limit: max=1, used=0 ("Maximum number
   of dedicated servers"). The quota is NOT zero; nothing is in use,
   so a SINGLE dedicated allocation fits within it. The 10x 10001 is
   therefore NOT a quota rejection — it points to physical
   dedicated-server STOCK in us-east-2 (or the dedicated fleet not
   being served there), with default tenancy as the capacity control.
   Consequences: (a) a single-node redeploy needs no quota change if
   stock ever appears — the retry/CreateVms path is unblocked on the
   entitlement side; (b) the full MS-5 2-node co-located pair still
   needs dedicated_server_limit >= 2 → the quota request stands for
   the pair; (c) the support ask should be reworded from "raise
   quota" to "dedicated server availability in us-east-2" (cc
   TAM/sales-eu@outscale.com).
