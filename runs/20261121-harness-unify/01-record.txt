== 5. TWO IMPLEMENTATION DEFECTS FOUND AND FIXED (the sw-suite's
first-ever execution — MS-6 gate doing its job) ==
Validation: unified sw-suite smoke on the held node
(PORCHE_BIN_DIR=/var/lib/porche/bin, SW_LOOP_CYCLES=5,
SW_ROLLBACK_CYCLES=3, SW_RECREATE_CYCLES=3, SW_CONCURRENCY=5).

First run: rollback cleanliness FAILED (volume region residue, all
cycles). Diagnosis chain (all verified live on the node):

  a) fallocate --dig IS NOT a punch-hole. util-linux getopt accepts
     "--dig" as an unambiguous PREFIX of --dig-holes ("detect ZEROES
     and replace with holes") — and the LUKS-erased header is RANDOM
     data, so nothing was ever zero: the punch NO-OPED since MS-1.
     Every "region_trimmed: true" in every wipe report since MS-1 was
     the exit code of a no-op. Empirical proof on the node:
     16 MiB random file → fallocate --dig --length N → du unchanged
     (16M); fallocate -p --length N → du 0.
     FIX (volume.rs): -p (punch-hole). The E-6 SECURITY claim
     (crypto-erase: keyslots + header destroyed) was NEVER affected —
     only the discard/space-reclaim step silently never ran.
  b) teardown never unlinked the region file. Wipes left the (erased,
     non-holed) region file behind — the MS-3/MS-5 1,000-cycle loops
     accumulated 1,010 husks / 16 GB on the node (measured; the
     retained extents are exactly the LUKS header area, ~16.5 MiB/file
     — consistent with (a)).
     FIX (exec.rs): after a CLEAN crypto-erase + trim, unlink the
     region file (FR-3 "no residue"); on a failed erase the file
     stays for the probe.

Post-fix validation (agent rebuilt — unit tests 41/41 green, sha256
2b77b6a1802a1e9fe4f34ebf72f67ab123befbf737a4a50465f2c92b71dffff3,
redeployed to /var/lib/porche/bin/porche; husks removed): the same
smoke — ALL GATES PASS (loop/drift/wipe-probes/rollback/idempotency/
concurrency), and the volumes dir ends at 0 files / 36K.
